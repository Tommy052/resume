GPU 기반 시각화 엔진 자체 개발

기존 데스크톱 분석 프로그램이 담당하던 검사 뷰어(ECT, IRIS 등)를 웹으로 대체하는 프로젝트. 검사 종류마다 데이터 규모와 시각화 요구가 달랐고(ECT는 멀티채널 라인 차트, IRIS는 대용량 히트맵), 인터랙션 요구는 점점 늘어났다. 단일 라이브러리로 모든 케이스를 커버하기가 어려웠다.

  • Plotly.js → D3.js 엔진 자체 설계 → WebGL GPU 렌더러 3개 패키지 직접 개발 (히트맵, 데이터 히트맵, 스트립/라인 차트)
  • LOD 다운샘플링, 텍스처 타일 분할로 GPU 메모리 한계 극복
  • 2D 맵의 3D 시각화를 위해 Babylon.js + WebGPU 기반 3D 뷰어 구축
  • D3.js + SVG 대비 렌더링 성능 약 10배 향상, 수십만 포인트에서 60fps 유지
  • 고정 3개 → 검사자가 자유롭게 차트 선택·배치하는 구조로 전환
  • 2D → 3D 맵 확장으로 검사 데이터의 입체적 분석 가능, 고객 만족도 확보

결정 과정 (단계적 진화):

  1. ECT 검사 뷰어 (1차 프로젝트): 기존 데스크톱 ECT 뷰어를 웹으로 이식 → Plotly로 시작 → 커스텀 인터랙션 자유도 부족으로 D3 자체 구성으로 전환
  2. ECT 뷰어 내 차트 15개 동시 렌더링 시 성능 이슈 → D3 + SVG 렌더링 최적화로 해결
  3. IRIS 검사 뷰어 (2차 프로젝트): 처음엔 ECT처럼 D3로 시도 → IRIS는 검사 파일 크기 자체가 ECT 대비 크고 히트맵 특성상 드래그/줌 시 실시간성이 떨어졌음 → WebGL GPU 히트맵 PoC 진행, 큰 폭의 성능 향상 확인 후 도입
  4. 2D 정면 맵을 입체로 보고 싶다는 니즈 → 튜브프로 형태 참고, 웹에서 최대 성능 내기 위해 Babylon.js + WebGPU로 3D 뷰어 구축, 고객 검증 통과

배운 점: 처음부터 WebGL/Babylon으로 가지 않은 게 결과적으로 올바른 선택이었다. 검사 종류마다 데이터 특성이 달라서, 단계마다 실제 병목을 확인하고 다음 기술로 넘어갔기 때문에 과도한 엔지니어링 없이 필요한 만큼만 복잡도를 추가할 수 있었다. 조기 최적화 유혹에 휘둘리지 않고 "지금 쓰는 기술의 한계"가 명확해질 때마다 다음 스택으로 갈아탄 것.

모노레포 전환 및 TypeScript 마이그레이션

동일 솔루션의 변형 프로젝트가 늘어나면서 4개 레포에 중복 코드 산재, 공통 UI 수정 시 레포마다 각각 수정·배포 필요. JS 기반 런타임 타입 에러 빈번.

  • Turborepo + pnpm 모노레포 통합 (현재 apps 6개 + packages 13개), 공통 UI 20+ 컴포넌트 분리
  • TypeScript strict 모드 전면 적용
  • 공통 UI 1회 수정으로 전체 앱 반영, 신규 화면 평균 개발 일수 마이그레이션 전후 비교 약 40% 단축
  • Sentry 기준 마이그레이션 전후 런타임 타입 에러 90% 이상 감소

결정 과정: 프로젝트 수가 늘면서 공통 컴포넌트·유틸의 재사용과 일관된 개선이 더 가치 있어진 시점이라고 판단. 모노레포로 통합해 "한 번 개선하면 모든 앱에 반영되는" 구조로 설계.
배운 점: TypeScript strict는 점진적 도입보다 일괄 마이그레이션이 결국 빨랐다. 중간 상태(any 허용 + 일부 strict)는 두 방식의 단점만 가지며 팀원들이 타입 배우는 동기도 떨어짐.

인프라 구축 및 DevOps

합류했을 때 서버 인프라가 없었다. 배포는 수동이었고, 장애는 고객이 알려줘야 알았다. GCP VM에 Bastion을 두고 Private 서버로 들어가는 네트워크를 설계한 뒤 Jenkins CI/CD로 배포를 자동화했다. 서버는 Prometheus + Grafana로, FE 에러는 Sentry로 각각 보이게 만들었다. 배포 시간은 30분에서 5분으로, 장애 인지는 수 시간에서 5분 내로 줄었다.

Electron 오프라인 데스크톱 앱

웹 솔루션을 운영하던 중, 일부 고객사 검사 현장에서 네트워크 없이 판독해야 한다는 요구가 들어왔다. 네이티브 데스크톱 앱을 새로 만드는 안과 기존 웹 자산(FE·BE·ML)을 재활용하는 Electron 패키징 안을 놓고 후자를 골랐다. 출시 속도와 이중 유지보수 회피가 결정 요인이었다.

FE + BE + ML 패키지를 단일 앱으로 묶어 오프라인 Windows 앱으로 빌드했다. 기존 웹 코드는 손대지 않고 IPC 경계만 새로 설계했다. 웹 코드 85%를 재사용해 별도 네이티브 개발 없이 출시했고, 오프라인 고객사를 신규 확보했다. 웹과 데스크톱이 같은 코드베이스를 쓰니 신규 기능 개발 비용도 이원화되지 않았다.

배운 점: "코드 85% 재사용"이라는 숫자보다 IPC 경계 설계가 본질이었다. 초기에 인터페이스를 평탄하게 잡아둔 덕에 후반 디버깅 시간이 크게 줄었고, 웹과 데스크톱 양쪽에서 같은 계약을 유지할 수 있었다.

Rust · Tauri 실시간 검사 수집 프로그램

와전류(ECT) 검사 장비를 제어하는 수집 프로그램이 레거시였고, 현장에서는 수집 → 신호처리 → 시각화가 한 화면에서 실시간으로 돌아야 했다. 장비 드라이버 DLL 직접 제어와 고속 스트림 처리는 기존 웹 스택으로 감당할 수 없었다.

  • Rust + Tauri v2로 데스크톱 앱 구축, 장비와는 ZMQ SUB 수신 + C FFI(드라이버 DLL) 하이브리드로 연결
  • 수집 시 10개 스레드 파이프라인 설계 (수신 → 파싱 → 그래프 실행 → 바이너리 프레임 방출), crossbeam 채널 단방향 연결 + UI 방출 단일 워커 직렬화
  • Scale(증폭·회전) · Mix · Filter를 컴파일드 DAG로 실시간 실행, 진폭·위상 알람 엔진과 장비 바이너리 포맷 Import/Export 구현
  • 프론트는 기존 웹 뷰어 자산(스트립 차트, 리사주, 깊이 곡선) 재사용, setup / inspection / analysis 3개 모드로 분리
  • 장비 제어부터 판독까지 단일 데스크톱 앱으로 통합, 웹 뷰어와 시각화 코드 공유
  • Rust 백엔드로 실시간 수집 경로 확보하면서 UI는 기존 React 자산 그대로 유지

배운 점: 병목이 연산량에 있을 거라 보고 파이프라인 단계를 나눴는데, 정작 깨진 곳은 UI 이벤트 방출 쪽이었다. 스레드마다 직접 emit하니 프레임 순서가 뒤섞였고, 방출을 단일 워커에 몰고 나서야 순서가 잡혔다.

자체 DWG 디코더 및 웹 CAD 플랫폼

플랜트 배관 검사 SaaS는 도면(P&ID · ISO)을 웹에서 읽고 편집해야 했는데, 고객이 제공 가능한 입력은 DWG와 PDF뿐이었다(중간 포맷 제공 불가). 상용 CAD SDK는 웹/SaaS 배포를 허용하는 티어의 연 라이선스 비용이 부담이었고, Go 바인딩이 없어 별도 마이크로서비스를 세워야 했다.

  • Go로 DWG 바이너리 디코더를 직접 구현하고 gRPC 파싱 사이드카로 분리 (NestJS BE + React/Three.js 2D 뷰어와 프로세스 경계 분리)
  • 자체 네이티브 CAD 포맷을 원본으로 두고 DWG는 1회 import 전용으로 격하 → 편집·버전 관리는 자체 포맷에서 수행
  • 도면 종류 체인(PFD → P&ID → ISO)을 라인넘버 조인키로 잇는 3-Way 매칭 파이프라인 설계
  • 고객 실도면 69장 전수 검증 — 열기 실패 0건, 재파싱 간 파싱 엔티티 수가 한 개까지 일치
  • INSERT 블록 전개 0% → 100% (블록을 정의와 배치로 나눠 담는 구조로 전환)
  • 상용 CAD SDK 라이선스 비용 $0, DWG R2010 · R2013 · R2018 판본 지원
  • 4개월간 파서 · BE · 뷰어 · 에디터를 단일 모노레포에서 병행 개발

결정 과정: "도면 뷰어를 만들 것인가, 데이터 조립 파이프라인을 만들 것인가" 에서 후자를 택함. 이 시스템의 최종 출력은 AI 부식 예측이 소비할 서킷 데이터라, 렌더링 충실도를 올리는 것보다 "라인넘버로 도면 간 조인이 되는가" 가 성패를 갈랐다.
되돌린 결정: 뷰어 초기에 오픈소스 CAD 구현에서 대좌표 렌더링 기법(좌표 rebase + RTE 셰이더)을 가져와 400줄가량 붙였다. 나중에 "우리 도면에 이게 실제로 필요한가" 를 다시 물어 좌표를 재보니, 배관 아이소메트릭 도면은 Float32 정밀도 문제가 생길 스케일이 아니었다. 그 기법은 정유소 부지 도면과 UTM 좌표를 전제로 설계된 것이었다. 셰이더 호환 디버깅에 쓴 시간까지 포함해 전부 걷어냈고, 이후로는 외부 구현에서 기법을 가져오기 전에 우리 데이터 샘플을 먼저 재보는 절차를 뒀다.
배운 점: 자체 디코더의 진짜 리스크는 못 여는 파일이 아니라 조용히 틀리게 읽는 파일 이었다. 미지원 판본은 에러 없이 레이어가 통째로 빈 채 들어왔다. 이후 검증 기준을 "열렸는가" 에서 "무엇을 무엇과 대조해 셌는가" 로 바꿨다.
